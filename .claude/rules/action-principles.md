# 行動原則

## 着手前に 4 点を固定する

- ゴール: 何を達成するのかを明文化する
- 背景: なぜこれをやる必要があるかを押さえる
- やらないこと: 踏み込まない範囲（スコープ外）を引く
- DoD: 達成できたかどうかを判定する条件を定義する
- 完了時には DoD を満たしたかを必ず確認する
- 理由: 目的・理由・スコープ・達成基準を最初に固めないと、走り出してから迷い・抜け・やりすぎが起きるため

## システムと AI を切り分ける

- 100 パーセントの再現性が必要なものはシステム（プログラム）として作る
- コード規約のように lint で自動化できるものは必ず自動化ツールを作る
- 定形作業は shell スクリプトや skill にする
- 抽象度の高いニュアンス対応、融通の利く振る舞い、人間に近い判断は AI に任せる
- 「どちらの担当か」を明確に切り分けて対応する
- 理由: システムは 100 パーセント再現性が強み、AI は柔軟性が強み。担当を分けないとどちらの強みも活かせないため

## 確証ベースで動く

- 推論や仮説で実装に入らない
- 既存の機能・仕様を必ず確認してから手を動かす
- 「確信が持てた」と言える状態になるまで調査を続ける
- 理由: 仮説で組み立てると、既存機能の重複実装やバグ混入が頻発するため

## 後方互換を残さない

- 暫定対応・残骸を残さない
- 旧 API / 旧コード / 旧設定は呼び出し元まで全て置き換える
- 「あとで消す」TODO を残さず、その場で消し切る
- 理由: 中途半端な対応がゴミの温床になり、根本対応の妨げになるため

## 現在の状態だけを書く

- ドキュメントやコードに歴史・経緯を残さない
- 「今一番きれいな状態」のみを表現する
- 履歴は git log に任せる
- 理由: 新しいセッションが最初に把握したいのは「今どうなっているか」のため

## ノウハウは共有資産にする

- 残したい知見は CLAUDE.md / rules / skill に書く
- 再現性のある手順は skill 化する
- 再現性がプログラムレベルで担保できるなら shell スクリプトも同時に作る
- shell は skill ディレクトリと同じ場所に置き、skill から呼び出す
- memory はプロジェクト共有資産として扱う（個人持ちにしない）
- 理由: ノウハウはプロジェクトとして蓄積・共有されてはじめて価値が出るため

## コードはテスト駆動で書く

- 先にテストを書き、テストを「あるべき姿の定義書」として機能させる
- テストコードを充実させ、プロジェクトを守る基準にする
- 理由: テストが定義書として機能しないと、プロジェクトの仕様が守られないため

## 環境変数のフォールバックは書かない

- 未設定なら例外を投げる
- デフォルト値で補完しない
- 理由: フォールバックは対応漏れの隠蔽になる。エラーで検知できる状態を保つため

## ゴミ掃除を徹底する

- 未使用のコード・関数・型・ドキュメントを削除する
- 削除を恐れない
- 理由: 不要物を残すと大事なものが薄まり、技術負債の温床になるため

## ドキュメントは視覚的に伝える

- 図・絵を中心に使う
- 文字は図の補足として最小限にする
- どうしても文字で書くときは 1 文を短くする
- 短文を箇条書きで縦に並べる
- 同じ流動を持つものはインデントを揃え、構造を直感的に捉えられるようにする
- 理由: 文字だらけの資料は覚えきれず、誤解や勘違いを生むため

## ユーザー発言の事実だけまとめる

- 想像力でユーザーを置いていかない
- 要約はしてよいが、勝手な追加・拡張・一般化はしない
- 理由: 勝手に追加した内容はユーザーのためにならないため

## 他のセッションを邪魔しない

- 複数 Claude Code セッションの同時起動が前提
- 他セッションの作成物を削除・上書きしない
- 作業前に他セッションが動いていないか意識する
- 理由: 誤って他セッションの成果物を破壊するリスクを避けるため

## プラグイン採用基準

- star 1000 以上であること
- 直近 6 ヶ月以内にメンテナンスされていること
- 理由: 人気・信頼・継続メンテによって外部依存の信頼性を担保するため
