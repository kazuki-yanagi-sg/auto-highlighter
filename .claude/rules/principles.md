# 実装規約

## Claude Code のミッション

**焦らず根本的に対処する。これがミッション。**

### 根本解決の原則

- 問題の表面的な症状ではなく、根本原因を特定し解決する
- 一時的な回避策や対症療法ではなく、持続可能な解決策を提供する
- 速さより確実性を優先し、品質の高い実装を行う

## 必ずやること

1. **early return のワンライナー化**

2. **必ず根本解決を行う**
   - 問題の症状を隠蔽する対症療法は厳禁
   - エラーを無視・回避するのではなく、根本原因を特定・解決する

3. **確認作業を怠らないこと**
   - 実装後は必ず動作確認
   - テスト実行で品質確認
   - コードレビューの視点で自己チェック
   - エッジケースの考慮

4. **一貫性を持つこと**
   - 同じ問題には同じアプローチ
   - 既存パターンの踏襲
   - 命名規則の統一
   - コーディングスタイルの統一

5. **確認したうえで、修正が不要と判断することも大切**
   - 問題を確認した結果、修正不要と判断できる場合がある
   - 「修正不要」も立派な判断結果
   - 理由を明確にして報告する
   - 過剰な修正は新たな問題を生む

6. **3 回見直しの原則**
   - **1 回目**: 実装直後の確認（構文エラー、基本動作）
   - **2 回目**: テスト実行後の確認（意図通りの動作、エッジケース）
   - **3 回目**: コミット前の確認（コード品質、一貫性、不要コード削除）
   - 各段階で異なる視点で見直す

## コード実装の 5 原則

1. **DRY**（重複削除）
2. **YAGNI**（不要機能削除）
3. **KISS**（簡潔化）
4. **SOLID**（単一責任）
5. **可読性・保守性**

リファクタリング時は **DRY → YAGNI → KISS → SOLID → 可読性** の順で適用する（重複削除を最優先、可読性は最後の磨き）。

## 関心の分離（最重要）

senri-core-system は **ロール別分離 + ドメイン凝集** で構成する。

- **ロール分離（Backend）**: 認可は `api/src/<domain>/endpoints/{admin,manager,member,common}/` のディレクトリ分割で表現する。1 ファイルにロール混在禁止
- **URL ロール分離**: `/api/v1/{admin,manager,member,common}/...` で分ける
- **ドメイン凝集（Backend）**: 1 ドメインの全要素（`models.py` / `factories.py` / `schemas.py` / `services.py` / `endpoints/`）を `api/src/<domain>/` 配下に集約
- **階層単方向（Frontend）**: `lib/api → servers → substances → organisms → molecules → atoms` の単方向依存（ESLint で機械検出）
- **判断軸**: 「このコードがどのドメインに属するか / どのロール向けか」を最初に決めてから書く
