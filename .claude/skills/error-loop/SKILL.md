# error-loop — エラー解析ループ

エラーを毎回手で調べる手間をなくすための手順。**この手順を厳密に順番どおり**に実行する。

## 入力
- 解析対象のエラー文(ユーザーが貼ったもの、またはツール出力/ログから観測したもの)。

## 手順

### 1. エラー内容を調べて意味を理解する
- エラー文・スタックトレース・関連するログ(`docker compose logs <svc>` 等)を読む。
- 必要なら該当コードを Read し、どの分岐でエラーが出ているか特定する。
- 「何が・どこで・なぜ」起きたかを1〜2文で言語化してから次へ進む。

### 2. errors.md を作成し、考えられる原因をすべて書き出す
- プロジェクト直下の `errors.md` に**追記**する(無ければ新規作成)。
- 1エントリ＝1エラー。次の形式で書く:

```markdown
## <日付/時刻> <エラーの1行要約>

**症状**: <観測した実際のエラー文>
**理解**: <何が・どこで・なぜ>

### 考えられる原因(可能な限り列挙)
- [ ] 原因1: <内容> — 検証/対策: <どう試すか>
- [ ] 原因2: ...
- [ ] 原因3: ...

### 試行ログ
```
```

- 原因は**思いつく限り**列挙する(確度の高い順に並べる)。

### 3. 上から1つずつ修正を試す
各原因について:
1. その原因を検証する最小の確認を行う(ログ確認・再現コマンド・1行調査)。
2. 対策を実装する(コード/設定の修正)。
3. **再現コマンドを実際に再実行**して直ったか確認する。
4. 結果を errors.md の「試行ログ」に1行で記録し、該当原因のチェックボックスを更新する
   (`[x] 解決` / `[-] 効果なし`)。
   - (a) **直ったら終了**(手順5へ)。
   - (b) **直っていなければ**次の原因へ。リストを使い切るまで繰り返す。

### 4. それでも直らなければ再調査
- リストの原因を全て試して直らない場合、**もう一度**エラー(と新しく得た情報・新しいエラー文)を
  調査し、考えうる原因を errors.md に追記して、手順3のループに戻る。
- 同じ対策の無限ループを避けるため、試したことは必ず試行ログに残す。

### 5. 完了通知
- 再現コマンドが成功した(エラーが完全に消えた)ことを確認したら、errors.md の該当エントリに
  `**結果: 解決** — <効いた対策>` を書く。
- **ユーザーに「エラーが直った」ことを明示的に知らせる**(何が原因で・何を直したかを一言添える)。

## 原則
- 「直ったつもり」で終わらせない。必ず**元の再現手段で再実行**して確認する。
- 推測だけで複数箇所を同時に変えない。1原因＝1変更＝1検証。
- TDD対象のコードを直す場合は、可能なら先に失敗するテストを足してから直す(CLAUDE.md準拠)。
