# 観点ベース リファクタリングスキル

リファクタリング観点を**1つだけ**選定し、その観点に絞ってプロジェクト全体を根本的にリファクタリングするスキル。本番稼働中プロジェクトのため、選定段階で影響範囲・リスクを必ず明示する。

## 観点蓄積ファイル

- パス: `.tmp/refactor-perspectives.md`
- 役割: 対応済み観点を蓄積する。次回起動時の重複回避と履歴参照に使う
- `.tmp/` は `.gitignore` 対象。ローカル専用でリモートに出さない
- ファイルが無ければ新規作成する

### エントリ形式

```markdown
## {YYYY-MM-DD} {観点名}

- 選定理由: {なぜこの観点を選んだか}
- 想定影響範囲: {どのレイヤー / ディレクトリ / 機能に影響しうるか}
- 想定リスク: {壊れた場合に影響する業務シナリオ}
- PR: #{番号}（PR 作成後に追記）
```

詳細な変更内容や対象ファイル数は書かない。git log / PR を見れば足りる。

## 実行フロー

### 1. 観点ファイル読込

```bash
.claude/skills/refactor-perspective/scripts/init-perspective-file.sh
```

その後 `.tmp/refactor-perspectives.md` を Read し、過去に対応済みの観点をすべて把握する。

### 2. 新規観点を1つ自律選定

プロジェクト全体を調査し、過去観点と重複しない観点を**1つだけ**選ぶ。粒度は「プロジェクト全体を貫いて適用できる横断的なルール / 構造の問題」。

選定の手がかり（例。実情に合わせて選ぶ）:

- TypeScript: `as` cast / `any` 残存箇所の一掃
- 命名規約違反（略語、`Props` 型名の不統一など）
- 重複ロジック・車輪の再開発
- 過剰なコメント・docstring
- 未使用 export / dead code
- Backend のエンドポイント分離違反（manager / member / common の混在）

ユーザー承認は取らない。スキル内で決め切る。

### 3. 観点ファイルに追記

着手前に `.tmp/refactor-perspectives.md` へ新規エントリを追記する。PR 欄は空のまま残す。

### 4. ブランチ作成

```bash
git switch -c refactor/{観点を表す英語スラッグ} develop
```

### 5. プロジェクト全体に対して根本対応

- 選定した1観点に絞る。他の観点に手を出さない
- 部分対応で打ち切らない。検出した違反箇所はすべて潰す
- 既存ルール（`.claude/rules/`, `CLAUDE.md`）に従う
- 破壊的更新を恐れない。後方互換のためのワークアラウンドは入れない

### 6. バグ発見時の扱い

リファクタリング中にバグを発見した場合は**その場で直さない**。必ず GitHub issue として切り出す。

```bash
gh issue create --label bug --title "{症状}" --body "$(cat <<'EOF'
## 再現手順
- ...

## 期待挙動
- ...

## 実挙動
- ...

## 発見経緯
refactor-perspective スキル実行中（観点: {観点名}）に発見
EOF
)"
```

すぐ直せそうでも例外なく issue 化。現スコープにバグ修正を混ぜない。

### 7. 品質確認

```bash
.claude/skills/refactor-perspective/scripts/quality-check.sh
```

API lint / Client lint / API test / Client test を一括実行する。すべて通るまで進めない。

### 8. コミット・push・PR 作成

まず PR 本文を `.tmp/pr-body.md` に書き出す（日本語）。

```bash
cat > .tmp/pr-body.md <<'EOF'
## 観点
{観点名}

## 対応内容
{1〜3行で要約。詳細は diff 参照}

## 影響範囲
{想定影響範囲}

## リスク
{想定リスクと、それに対する確認方法}
EOF
```

その後 shell を呼ぶ。コミットメッセージは英語、PR タイトル・本文は日本語（CLAUDE.md のルール）。

```bash
.claude/skills/refactor-perspective/scripts/commit-push-pr.sh \
  "{英語の要約}" \
  "{観点名}" \
  .tmp/pr-body.md
```

出力された PR URL から PR 番号を取得し、次ステップで使う。

### 9. 観点ファイルに PR 番号追記

```bash
.claude/skills/refactor-perspective/scripts/append-pr.sh "{観点名}" {PR番号}
```

該当エントリの `- PR:` 行に `#{PR番号}` を埋め込む。

### 10. 3周レビュー

PR の diff を**観点を変えて3回**読み直す。

- 1周目: 観点ブレ・スコープ逸脱がないか（他の観点に手を出していないか）
- 2周目: 漏れ（観点に該当する違反箇所が残っていないか、grep で再確認）
- 3周目: 壊していないか（業務挙動を変えていないか、import / 呼び出し元の整合性）

修正が必要な箇所は実際に修正し、追加コミットして push する。3周完了で最終形。

## 禁止事項

- 1回の実行で複数観点に手を出す
- 過去観点と重複した観点を選ぶ
- 観点ファイルへの追記をスキップして実装に入る
- バグ発見時に現スコープで修正する（必ず issue 化）
- 部分対応で打ち切る
- 3周レビューをスキップする
