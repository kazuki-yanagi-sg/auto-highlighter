# bug-issue-fix

GitHub の bug ラベル issue を1件、**影響範囲と類似箇所まで含めて根本対応**し、develop ベースの PR を作成するところまでが責務。マージ・整理は責務外で、完了後 `merge-and-cleanup` に引き継ぐ。

## 適用条件

- 対象は bug ラベルの issue のみ。仕様変更要望・機能追加・調査依頼と判明した時点で中断し、ユーザーに報告する
- 起動時に issue 指定が無ければ `gh issue list --state open --label bug` から1件選定する
- 推測で着手しない（事実ベース、CLAUDE.md 行動原則準拠）
- 後方互換ワークアラウンドを入れない（根本対応）

## フロー

### 1. issue 選定と理解

ユーザーから issue 指定が無ければ `gh issue list --state open --label bug` から自分で1件選ぶ（選定理由は PR 本文に書く）。

`gh issue view <番号> --comments` で本文・コメント・関連 PR を読む。あわせて **assignees / 関連 open issue / 関連 open PR** を確認し、二重着手や既知の依存（「#XXXX と同時対応の方が一貫」のような記述）を見落とさない。業務観点で「何が起きていて、何が期待挙動か」を1〜2行で言語化する。言語化できなければ起票者確認をユーザーに依頼して停止する。

### 2. 原因箇所の特定

再現条件（入力データ・実行ロール・呼び出し経路）と原因 lines を `find_symbol` / grep で実コードに到達して確定する。「たぶんここ」で止めない。

### 3. 影響範囲調査

下記の観点で必ず確認し、結果をチャットに事実として列挙してから次に進む。

| 観点 | 確認手段 |
|---|---|
| 呼び出し元 | `find_referencing_symbols` / grep |
| ロール別経路 | `endpoints/{manager,member,common}` に同種ロジックが無いか |
| データフロー | 入力 → モデル → API レスポンス / DB 書き込み / 関連テーブル |
| フロント影響 | substances / organisms 配下で該当 API を叩く層 |
| 既存テスト | 何を担保していたか・どこが手薄か |

### 4. 類似パターンの網羅探索（このスキルの肝）

1件直して終わりにしない。原因コードのパターン（条件分岐の欠落・例外処理漏れ・フィルタ漏れ・型の扱い 等）を抽象化し、同型の箇所を別ファイルに広げて探す。

- manager 側のバグ → member / common に同型が無いか
- 1つの API のフィルタ漏れ → 他の同系統 API にも漏れが無いか
- 同じユーティリティを使う全呼び出しに同じ問題が伝播していないか

見つけた類似箇所はリストアップしてユーザーに提示し、**同一 PR にまとめるか / 別 PR に切り分けるか** を確認する。**該当なしと判断した場合も、その旨を明示する**（探索した事実を可視化する）。

### 5. 実装

修正方針をチャットで宣言してから着手する。仕様としてのテストを先に書き、類似箇所も同 PR に含める（ユーザーが分割を選んだ場合を除く）。

### 6. 検証

プロジェクト規約に従って lint / test / 型チェックを通す（CLAUDE.md「コマンド」参照）。DB スキーマ変更があれば prisma → model → alembic の手順を守る。

### 7. PR 作成

`gh pr create --base develop` で PR を作る。タイトル・本文は日本語。本文には PR レビューで内容確認できるよう、**判断・調査の過程まで含めて** 書く。骨子:

- 概要（バグの概要と修正方針。複数案あった場合はなぜその案を採ったか1行）
- 対応内容（直接原因 + **類似箇所の同時対応の有無を明記**。該当なしの場合も「調査し該当なし」と書く）
- **横展開調査の観点**（必須）
  - どんなパターンで類似を探したか（例: ロール別エンドポイント / 同系統 API / 同ユーティリティ利用箇所 / フィルタ漏れパターン）
  - 調査対象にした範囲（ファイル / モジュール / ロール別ディレクトリ）
  - 各観点ごとの該当有無と、該当ありの場合の対応方針（同 PR / 別 PR / フォローアップ起票）
- 影響範囲（呼び出し元・データフロー・フロント影響）
- テスト観点
- `Closes #<issue番号>`（複数 issue を解決する場合は **1行ずつ** 書く。別 PR に切り分けた類似箇所はフォローアップ issue として起票し本文にリンクする）

## 完了条件

- [ ] 選定 issue を1〜2行で言語化済み
- [ ] 原因箇所を行レベルで特定済み
- [ ] 影響範囲を観点ごとに事実列挙済み
- [ ] 類似箇所を網羅探索し、**横展開調査の観点・調査範囲・該当有無** を PR 本文に明記済み
- [ ] 仕様としてのテストが追加・更新されている
- [ ] lint / test 通過
- [ ] develop ベースの PR を `Closes #<issue>` 付きで作成済み

## やってはいけないこと

- issue を読まずに修正方針を立てる
- 類似箇所探索を省く（1件直して PR で終わる）
- 後方互換のためのフラグ・分岐を追加する
- ローカル検証を飛ばして PR を出す
- マージまで進める（責務外、`merge-and-cleanup` に渡す）
