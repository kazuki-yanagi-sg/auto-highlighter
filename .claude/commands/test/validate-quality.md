# テスト品質検証

## ゴール

1. **価値のないテストを排除** - ビジネス価値を検証しないテストは削除
2. **クリティカルパスの保護** - 重要機能に必ずテストが存在
3. **リファクタリング耐性を確保** - 実装詳細ではなく振る舞いをテスト

## 引数

- 引数指定時: 指定ディレクトリ/ファイルのテストのみ検証
- 引数未指定時: 現在ブランチで変更されたテストを検証

## 核心原則（Google Testing Philosophy）

**Beyoncéルール**: 「壊したくないものにはテストを書く」
- ⚠️ **重要**: 実装されている機能のみをテスト対象とする
- 存在しない機能や将来の機能はテストしない

**テストの目的**: バグを見つけるだけでなく、**変更を可能にする**ために書く

**懐疑的な目線**: すべてのテストに「これ本当に必要か？」を問え

**本質を問え**: 「このテストがないと、本番で何が起きるか？」

**削除を恐れるな**: 価値のないテストは負債。容赦なく削除せよ

## 実行手順

### 1. 哲学理解（必須）

以下を完全に読み込め：

- `docs/google-testing-philosophy.md`
- Backend: `api/docs/testing-philosophy.md`
- Frontend: `client/docs/testing-philosophy.md`

**理解すべき核心**:
- 価値あるテスト = ビジネスロジックを守るテスト
- **パブリックAPIを通じてテスト**: 実装詳細ではなく、ユーザーが使う方法でテスト
- **状態をテスト、相互作用ではない**: 何が呼ばれたかではなく、結果の状態をテスト
- アンチパターン = 実装詳細への過度な依存、モックの過度な使用

### 2. 現状分析

developブランチとの差分を分析し、以下を特定：

- 変更/新規作成されたテストファイル
- テストが未作成の新規ソースファイル
- 変更の影響範囲（ビジネスロジック/UI/インフラ）

分析結果に基づいて、TaskCreateでタスク計画を策定せよ。

### 3. 品質評価（核心）

各テストファイルを評価せよ：

```yaml
mcp__serena__find_symbol
  name_path: "test"
  relative_path: "[テストファイルパス]"
  include_body: true
  depth: 2
```

**評価基準**:

1. **価値**: ビジネス価値を守っているか？
2. **仕様性**: 実装ではなく「あるべき姿」を記述しているか？
3. **耐性**: リファクタリングで壊れないか？
4. **必要性**: このテストがないと本番障害が起きるか？

#### 懐疑的レビュー（最重要）

すべてのテストに対して問え：

```
このテストは本当に必要か？
このテストがないと、本番で何が起きるか？
ビジネスロジックを守っているか？それとも実装の確認か？
```

**即削除対象の例**:

```python
# ❌ Enum値の確認（言語機能のテスト）
assert consignee.prefecture.value == "tokyo"

# ❌ Trivialなgetter/setter
consignor = Factory(id=x)
assert consignor.id == x

# ❌ 長さチェック・自明な確認
assert len(value) > 0
assert "item" in [items]

# ❌ 「作成できる」のみ
obj = Factory()
assert obj.deleted_at is None

# ❌ モックの相互作用のみをテスト（状態ではなく）
mock_service.method.assert_called_once()
expect(mock_function).toHaveBeenCalled()
```

**判断基準**:
- 「このテストが失敗したら、ユーザーに影響があるか？」→ Noなら削除
- 「結果の状態をテストしているか？呼び出しをテストしているか？」→ 後者なら削除

### 4. 改善実施

#### ステップ1: 価値のないテストを削除

懐疑的レビューで特定したテストを削除：

- Enum値確認テスト
- Trivialなgetter/setterテスト
- 「作成できる」ことのみのテスト
- 長さチェック・メンバーシップチェック
- モックの相互作用のみをテストするもの（状態ではなく）

#### ステップ2: 既存テストの改善

価値はあるが品質が低いテストを改善：

- アサーションが不明確 → 明確なメッセージを追加
- テスト名が不適切 → ビジネス価値を表す名前に変更
- AAA構造が不明確 → Arrange/Act/Assertを明確化

#### ステップ3: 不足テストの作成

「壊したくないもの」で未保護のものを追加：

**必須作成対象（壊したくないもの）**:

1. **ビジネスロジック**: 料金計算、在庫計算、締日判定、権限判定など
2. **データ変換**: かな名自動生成、日付フォーマット変換、単位変換など
3. **エラーハンドリング**: 異常系のフォールバック、エラーメッセージ表示など
4. **認証・認可**: ログイン、権限チェック、データアクセス制御など
5. **クリティカルパス**: ソフトデリート、一意性制約、外部キー関連など

**判断基準**: 「これが壊れたら、ユーザー体験や業務に支障が出るか？」→ Yesなら作成必須

**作成時の注意**:
- **パブリックAPIを通じてテスト**: 実装詳細（privateメソッド等）ではなく
- **状態をテスト**: 何が呼ばれたかではなく、結果の状態を検証
- **実装されている機能のみ**: 将来の機能や存在しない機能はテストしない
- Factoryを活用し、モックは最小限に（外部依存のみ）
- AAA構造を守る（Arrange/Act/Assert）

### 5. 成果確認

改善後に確認せよ：

- 全テストがパスするか
- カバレッジが改善されたか（数値ではなく質的向上）
- テスト実行速度が許容範囲か

改善結果をレポートにまとめ、以下を明確にせよ：

- 達成したゴール
- 改善の具体的内容と効果
- 残存リスクと今後の課題

**テストコードを修正した場合、必ずcommit・pushまで完了させること**：

```bash
git add [修正したテストファイル]
git commit -m "test: テスト品質改善"
git push
```
