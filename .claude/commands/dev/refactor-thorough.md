# 徹底的リファクタリング

## ゴール

リファクタリングを実施

## 原則事項

- 徹底的な状況確認
  - 良いプログラムは徹底的な状況把握からしか生まれない
  - 推測やうろ覚えで対処しない。徹底的な確認から
  - **project_checkだけでは不十分。必ず実際のコードを読むこと**
- コードの深い理解が最優先
  - リファクタリング前に必ずコードを読んで理解する
  - 動作を理解せずにリファクタリングすることは禁止
  - テストコードがあれば必ず確認して期待動作を把握
- project_checkの絶対対応
  - エラーは絶対に後回しにしない
  - 量が多くても必ず対応
  - ただし、project_checkは補助ツール。メインはコード理解
- 絶対に妥協しないこと
  - 急いでないので、徹底的な根本的な対応を求める
  - それができるあなただからこそ依頼をしている

## リファクタリング観点

- 車輪の再開発の徹底排除
  - DRY原則の徹底
- 後方互換性の徹底排除
  - 今が完全な恒久対応のタイミング
  - 技術負債の徹底排除
- MECEの徹底
- シンプルでリーダブルなコードの徹底
  - 可読性、保守性は読みやすさから
  - 略語の徹底排除
- 過剰なdocstring, コメントの徹底排除
  - 効果的なコメントのみ残す

## 実行フロー

### 1. 徹底的な現状把握

**警告**: project_checkだけでは全体の状況は把握できない。必ず実際のプログラムコードを確認すること。

```bash
# 現在のブランチと変更内容確認
git status
git diff
git diff --cached
git log --oneline -10
```

#### 必須：プログラムコードの徹底確認

- **実際のコードを読む**: Readツールで関連ファイルを必ず確認
- **依存関係を把握**: importやrequireを追跡
- **実装パターンを理解**: 既存コードの書き方を徹底的に調査
- **動作を理解**: 単にlintを通すだけでなく、実際の動作を理解

```bash
# project_checkは補助的に使用（メインではない）
./project_check.sh
```

### 2. リファクタリング対象の分析

- 引数: $ARGUMENTS
  - 引数指定時: その対象に限定
  - 引数未指定時: 現在ブランチの修正範囲全体

#### 分析前の必須作業：コードの深い理解

1. **対象ファイルを実際に読む**（Readツール使用）
2. **関連ファイルも確認**（importされている/しているファイル）
3. **テストコードを確認**（期待される動作の理解）
4. **実行して動作確認**（可能な限り）

#### 分析観点（コードを理解してから実施）

- コード重複の特定（DRY違反）
- 車輪の再開発箇所の特定
- 技術負債・後方互換性のための汚いコード
- 略語・わかりにくい命名
- 過剰なコメント・docstring
- MECE違反（重複・漏れ）
- 複雑すぎるロジック

### 3. Taskツールでタスク管理

- 特定した改善点をすべてTaskCreateで記載
- 優先順位を決定（影響範囲の大きさ・改善効果）

### 4. 徹底的な実装

- 各改善点を根本から対応
- 表面的な修正は許されない
- 妥協は許されない

### 5. 品質確認

```bash
# 各改善後に必ず実行
./project_check.sh --client-lint
./project_check.sh --api-lint
```

### 6. 最終確認

```bash
# すべての改善完了後
./project_check.sh

# クリーンな状態確認
git status
```

### 7. 完了処理

- project_checkのすべて通過したらpush

```bash
git add .
git commit -m "refactor: 徹底的なリファクタリング実施"
git push
```

## 禁止事項

- 妥協した対応
- 表面的な修正
- 「とりあえず」の対応
- エラーを後回しにする
- project_checkのエラーを無視

## 使用方法

- `/dev:refactor-thorough` - 現在の変更範囲を徹底的にリファクタリング
- `/dev:refactor-thorough "client/src"` - 指定ディレクトリを徹底的にリファクタリング
